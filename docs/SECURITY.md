# নিরাপত্তা মডেল (Security Model)

## ১. হুমকি মডেল

হিসাবডেস্ক এমন একজন ব্যবহারকারীর জন্য যাঁর ফোনে আর্থিক তথ্য থাকে এবং যিনি চান:

- ফোন হাতে পাওয়া অন্য কেউ অ্যাপ না খুলতে পারে (UI lock),
- ফোন হারালে/বিক্রি করলে তথ্য অ্যাপের বাইরে না যায়,
- ব্যাকআপ ফাইল অন্যের হাতে গেলেও পড়া না যায়।

যা এই মডেলের **বাইরে**: root করা ডিভাইস, ম্যালওয়্যার, forensic extraction,
স্ক্রিন রেকর্ডিং, shoulder-surfing। কোনো অ্যাপই এগুলো সম্পূর্ণ ঠেকাতে পারে না।

## ২. PIN সুরক্ষা (প্রকৃত বাস্তবায়ন)

| বিষয় | বাস্তবায়ন |
|---|---|
| সংরক্ষণ | PIN কখনো সংরক্ষিত হয় না |
| ডেরিভেশন | `PBKDF2WithHmacSHA256`, ২,১০,০০০ iteration, ২৫৬-bit output |
| Salt | প্রতি PIN-এ ১৬-বাইট `SecureRandom` salt |
| তুলনা | `MessageDigest.isEqual` (constant-time) |
| অতিরিক্ত সুরক্ষা | verifier blob Android Keystore-এর AES-256-GCM key দিয়ে মোড়া (উপলব্ধ হলে) |
| ব্যর্থ চেষ্টা | ৩, ৪, ৫, ৬, ৭+ ভুলে ৩০s, ৬০s, ৫মি, ১৫মি, ৬০মি lockout |
| লক | ব্যাকগ্রাউন্ডে গেলে ব্যবহারকারীর নির্বাচিত সময় (সঙ্গে সঙ্গে/১/৫/১৫ মিনিট) |
| রিসেট | কোনো গোপন bypass বা recovery নেই (ইচ্ছাকৃত) |

**গুরুত্বপূর্ণ সীমাবদ্ধতা:** PIN শুধু UI লক। ডেটাবেজ নিজে এনক্রিপ্টেড নয়।
PIN ভুলে গেলে ডেটা উদ্ধারের কোনো উপায় নেই (ব্যাকআপ ছাড়া)।

## ৩. ডেটা at-rest

- Room/SQLite ফাইল Android app sandbox-এ (`/data/data/com.shohankhan.hisaabdesk/`)।
- `android:allowBackup="false"` — ADB backup ও ক্লাউড auto-backup বন্ধ।
- ফুল-ডেটাবেজ এনক্রিপশন (SQLCipher) ব্যবহার করা হয়নি; এটি স্পষ্টভাবে ডকুমেন্টেড
  (ভুল দাবি নয়)। সুরক্ষা নির্ভর করে:
  - Android app sandbox (অন্য অ্যাপ পড়তে পারে না),
  - ডিভাইস-স্তরের এনক্রিপশন (FBE; Android 10+ এ ডিফল্ট),
  - স্ক্রিন লক।
- root করা ডিভাইসে ফাইল পড়া সম্ভব — ব্যবহারকারীকে জানানো হয়েছে।

## ৪. এনক্রিপ্টেড ব্যাকআপ

```
HDBK1 | version=1 | saltLen | salt(16) | ivLen | iv(12) | AES-256-GCM(ciphertext||tag)
```

- Key = `PBKDF2WithHmacSHA256(ব্যবহারকারীর পাসওয়ার্ড, random salt, 210000, 256-bit)`
- প্রতি ব্যাকআপে নতুন random salt ও IV — একই key+IV পুনরায় ব্যবহৃত হয় না।
- GCM tag যাচাই ব্যর্থ হলে ভুল পাসওয়ার্ড বা ক্ষতিগ্রস্ত ফাইল — বিস্তারিত leak করা হয় না।
- পাসওয়ার্ড কোথাও সংরক্ষিত হয় না; ভুলে গেলে ফাইল খোলা যায় না।
- রিস্টোর: ডিক্রিপ্ট → পূর্ণ ভ্যালিডেশন (স্কিমা, টাইপ, সীমা, duplicate ID, FK) →
  এক DB transaction-এ প্রতিস্থাপন → ব্যর্থ হলে rollback (পুরনো ডেটা অক্ষত)।
- আপলোড/ক্লাউড: কিছুই নেই; ফাইল ব্যবহারকারীর নির্বাচিত জায়গায় যায়।

## ৫. কী ম্যানেজমেন্ট

- Android Keystore-এ non-exportable AES key (alias `hisaabdesk_master`)।
- Keystore অনুপলব্ধ হলে (কিছু ডিভাইস/এমুলেটর) verifier শুধু PBKDF2-সুরক্ষিত থাকে —
  অ্যাপ কাজ করে, নিরাপত্তা কিছুটা কমে (ডকুমেন্টেড, ব্যর্থতা ছাড়া)।
- কোনো key/PIN/পাসওয়ার্ড লগ করা হয় না।

## ৬. কম্পোনেন্ট ও প্ল্যাটফর্ম

- কোনো `INTERNET` অনুমতি নেই → ডেটা এক্সফিল্ট্রেশনের নেটওয়ার্ক পথ নেই।
- `usesCleartextTraffic` প্রয়োজন নেই।
- FileProvider শুধু app-private attachments/exports শেয়ার করে (`exported=false`)।
- সংযুক্তি: SAF পিকার ব্যবহারকারীর নির্বাচিত ফাইল কপি করে (প্রয়োজনে); কোনো
  external storage permission নেই।

## ৭. ঝুঁকি ও সীমাবদ্ধতা

1. ডেটাবেজ at-rest এনক্রিপ্টেড নয় (উপরের §৩)।
2. PIN brute-force ঠেকানো হয় throttle দিয়ে, হার্ডওয়্যার-ব্যাকড rate limit ছাড়া।
   PBKDF2 cost + lockout সম্মিলিত প্রতিরক্ষা।
3. `ADJUSTMENT`/`REFUND` ধরনের direction ব্যবহারকারীর নির্বাচন অনুযায়ী; ভুল ব্যবহারে
   রিপোর্ট বিকৃত হতে পারে (কিন্তু মোট ব্যালেন্স লেজার থেকেই আসে)।
4. Attachment ফাইল কপি করার UI এখনো সম্পূর্ণ নয় (প্রগতিশীল কাজ)।
5. Biometric unlock বাস্তবায়িত হয়নি (ইচ্ছাকৃত — ভুলভাবে আধা-সমর্থিত ফিচার না রাখা)।

## ৮. ব্যবহারকারীর জন্য পরামর্শ

- শক্তিশালী, অনন্য PIN ব্যবহার করুন (জন্মতারিখ নয়)।
- নিয়মিত এনক্রিপ্টেড ব্যাকআপ নিন এবং পাসওয়ার্ড আলাদা নিরাপদ জায়গায় রাখুন।
- ফোনের স্ক্রিন লক ও এনক্রিপশন চালু রাখুন।
- অ্যাপ আনইনস্টল করলে ডেটা মুছে যায় — ব্যাকআপ ছাড়া নয়।
